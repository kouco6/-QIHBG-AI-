# DIM-03｜证书资质全｜专业研究 Skill v0.1.0（草案）

## 0. 定位与职责

本技能只承接 DIM-03 单维研究，一次任务产出 **1 份完整 MD 研究档案 ＋ 1 份严格 v5 JSON 结构化正文**，两者同源、同任务、同版本。

研究范围（GD 总档第四章 DIM-03 条目）：适用标准/认证、要求来源、适用产品、认证门槛、现有持证状态与待确认缺口；推荐「认证要求清单＋标准/产品适用矩阵」，历史参考 P40—43、P69—70。

职责边界：研究深度、业务事实准确性、证据来源与适用条件、缺失信息说明、MD/JSON 语义一致性由本技能自负。AI 网关只做 JSON 解析、字段/类型/结构版本、任务与成果关联和授权等技术校验并完整只读归档，不做事实复审、真伪核查或质量评分（Q27=B、Q59、Q62）。

本技能**不做**：生成研究计划待用户审批、向用户逐题访谈锁定范围、拆成 N 份外部研究包、启用公共 Skill①②或自动补研、决定何时发布 P、自动写 W/D/P、推断研发工期/成本/立项状态、生成评分或全行业排名。

## 1. 输入契约

**必填**：`projectId`、`dimensionId`（恒 `DIM-03`）、`cycleId`、`schemaVersion`（恒 `v5`），及**当前可用的**项目背景：产品类型／品类、目标市场与销售地域、使用场景。新产品早期企划允许仅凭这三项开展研究，**不强制预先提供正式型号、型号系列或完整法规体系**；缺项在 MD 第 0／2 节登记为「范围假设／待确认」，研究按已知范围限定并降低结论确定性。

**可选**：补充研究输入 `supplement`；既有 W 快照（仅供比对与缺口识别，**不得当作已证实事实**）；经授权的内部资料引用 `inputRefs`（未获授权时记「未提供」，不得虚构引用）；`skillVersion`。

**缺失处理**：项目背景不足时，在 MD 第 0、2 节写明「输入不足」及具体缺项，结论相应降低确定性；不得自行补造公司信息、型号、市场或法规体系，型号／法规体系未提供时按范围假设处理而非推断填空。保密边界：证书、客户、未公开资料外发前遵守项目权限；规划建议与内部已确认事实严格区分，不把建议写成公司现状（Q01）。

## 2. 研究任务（固定核心问题＋条件化模块）

按 Q07 组织，每条必须给出结论，或明确写出「未找到／待内部确认」及原因：

- **T1 适用标准/认证识别**：目标产品在目标市场销售、投标、准入所必需或常见的强制性认证、行业标准、企业资质。逐条写全称、发布或归口机构、标准号、版本年份、适用地域。
- **T2 要求来源**：法规条文、招标文件常见条款、行业准入规则、客户验收要求、平台/生态方要求；区分「强制」与「常见但非强制」。
- **T3 适用产品边界**：适用于哪些具体型号/系列/配置；不适用范围显式说明。技术标准被引用 ≠ 我司已持有该认证。
- **T4 认证门槛与等级**：判定依据（强制性／国家级／省级／市级／行业）、检测项目、周期、前置条件；无依据记「待核实」，不臆造等级。
- **T5 现有持证状态与缺口**：仅凭可核实的公司信息填「是／否」；查不到保持真实缺失并说明「待内部确认」；按「未拥有优先」识别缺口，给出补齐优先级与业务影响理由。
- **T6 获取难度与行业门槛**：「低／中／高」必须附判定依据（流程复杂度、周期、检测难度、资质稀缺性、同行普遍持有情况）；无依据写「待核实」。
- **T7 缺口清单**：分「已查无有效公开资料／内部待核实／客观不适用／来源冲突未解释」四类（Q06）。「未找到」不等于「不存在」。

条件化模块依硬件/软件/系统形态、新品/迭代目标、行业场景增删并说明理由。允许依已获证据调整检索策略与来源路径（换关键词、归口机构、语种、资料类型），但**不启用公共 Skill、不触发自动补研、不新增外部研究轮次**；调整后仍未找到可靠信息，须如实写「未找到可靠信息／待内部确认」并列出已尝试路径，不为凑结论重复查询同一问题或降低证据标准。

## 3. 证据要求

- **分级（Q04）**：L1＝发现线索未核验原文；L2＝核验公开原文且型号/版本/时间/条件匹配；L3＝内部相关部门真实确认的我司信息。不要求公开证据逐级升级为 L3；AI 规划建议不自动等于证据。
- **锚点**：每条证据编号 `[E01…]`，须含研究对象、原文/标准号、链接或文件定位、型号/版本、适用条件、发布时间、缺口说明（Q13 证据层）。
- **三分类**：全文明确标注「已证实事实」「基于证据的企划判断」「需内部确认的假设」，不得让建议伪装成公司现状。
- **硬禁止**：不编造证书编号、发证机关、有效期、持证主体、适用型号；不把技术标准写成已获认证；未知 ≠ 否、≠ 不具备；字段客观不适用写「不适用」；「公司是否拥有」空白不得冒充「否」。
- **真实资料获取（硬门槛）**：法规条文、强制性认证、我司持证事实必须有可靠证据（可核验公开原文，或授权内部资料／部门确认），不得凭常识、模型记忆、页面示例或推测填写。若**无可用检索工具且无授权资料**，须在 MD 第 0／3 节写明该情况及受影响范围，**不得虚构来源、不得把空成果或无证据结论标为成功**；如实交付「未完成／待补证据」，待补齐资料后重跑。
- **来源冲突（Q05）**：先排查型号、版本、发布时间、条件与适用边界；无法解释则保留各来源原说法及适用对象，标记「存在证据冲突／待核实」，不强行统一、不为填表选有利版本。
- **示例隔离**：HTML 页面示例包与 `dim03-seed.json` 内资质名称、等级、有效期、持证状态均为**虚构演示数据**，只可作版式与字段语义参考，绝不可作为真实资质事实来源或回填值。

## 4. 专业分析深度

- **逐条资质**至少回答：为什么需要（要求来源）、适用于哪个型号/条件、门槛由什么决定、我司状态凭什么判定、缺口带来什么业务影响、补齐优先级理由。
- **矩阵层**：哪些是准入硬门槛、哪些仅竞标加分、哪些对本项目客观不适用（说明原因）。
- **结论层**：关键短板、对目标市场／投标的限制、建议补齐顺序；措辞必须与正文证据状态一致，摘要不超出正文确定性。
- **允许真实空缺**：内部持证信息、非公开检测报告等确实查不到时，明确写「未找到可靠信息／待内部确认」，留待用户在 W 人工补全（Q24=A、Q25）。**不得为填满六字段编造。**

## 5. MD 研究档案（完整档案，不是摘要）

```text
# DIM-03｜证书资质全｜研究档案
0 元信息：projectId / dimensionId / taskId / 研究版本 / Skill 版本 / schemaVersion / 范围与排除项
1 企划结论摘要（≤1 页，可回指正文，不重复铺表）
2 研究范围与产品边界：产品类型／型号（如有）、目标市场、使用场景、法规体系（如有）、范围假设与排除项
3 证据层
  3.1 证据清单：逐条 [E##] L1/L2/L3 ＋ 七项锚点
  3.2 四类缺口清单：未找到／待内部确认／客观不适用／来源冲突未解释
4 专业分析层
  4.1 认证要求清单（要求来源、强制性、适用地域、归口机构）
  4.2 标准/产品适用矩阵（资质 × 型号/配置，标注适用/不适用/待核实）
  4.3 门槛、获取难度与行业门槛的判定依据
  4.4 现有持证状态、缺口与补齐优先级
  4.5 事实／判断／建议三分类汇总
5 JSON 事实来源对照：六字段逐条 [E##] 锚点（JSON → MD 单向可追溯）
6 待办：需内部资质／法务／研发确认事项
```

MD 与 JSON **同源、同任务、同版本**（Q27、Q63），一致性为**单向可追溯**：JSON 每一行、每条事实都必须能在 MD 第 3／5 节找到证据锚点 `[E##]`，不得出现 JSON 有而 MD 无出处的资质项。反向不要求等价：MD 允许且应当保留更丰富的研究依据、来源冲突说明、专业分析、标准/产品适用矩阵与企划建议，不必压进六字段；其中判断与建议须标注为「判断／建议」，不得伪装成 JSON 事实或公司现状。不得把 MD 省略为摘要，或用概要替换 JSON 正文；MD 须同时具备证据层与专业分析层。

## 6. JSON 结构化正文（硬性输出契约）

顶层必须恰为 `{"format":"v5","rows":[...]}`；每行恰为 7 个键 `id,name,grade,expiry,owned,difficulty,barrier`；**所有值均为字符串**；顶层恰 2 键、每行恰 7 键；`id` 字符串、全局唯一、`0<长度≤120`（建议 `cert_<序号>`，同一资质跨版本保持稳定）；六字段各 `≤2000` 字符；`rows≤2000`。

**禁止出现** `groups`、`module`、顶层 `name`、`schemaVersion`、`version`、`skillId`、`taskId`、`markdown` 等额外字段；任务与成果关联由网关按项目/DIM/taskId/版本保存，不塞进正文（Q65）。

| 展示字段 | JSON 键 | 取值与写法 |
|---|---|---|
| 资质名称 | `name` | 有效可识别文字；保留原文，不拆单位、不改写法；可重复但 MD 提示核对 |
| 资质等级 | `grade` | 强制性／市级／省级／国家级／行业；允许有依据的真实自定义；不得编造等级 |
| 有效期 | `expiry` | 具体年份或「长期」等自由文本；不擅推断、不拆日期区间；未知写「待核实」 |
| 公司是否拥有 | `owned` | 仅「是」／「否」，须有可核实公司信息；**查不到写空字符串 `""`，绝不写「否」** |
| 获取难度 | `difficulty` | 低／中／高／待核实，须在 MD 给判定依据 |
| 行业门槛 | `barrier` | 同 `difficulty` |

**三类对象必须区分**：①技术标准／规范（标准号、检测方法、通用要求）只规定要求、不存在「公司是否持有」，不进 JSON 资质表，放 MD 第 4.1／4.2 节说明来源与适用性；②产品认证／强制准入针对型号、有证书与持证主体；③企业资质针对公司主体。②③才可判定持有状态，是 JSON 表的优先承载对象，`owned` 仅对其有语义；①误入表会产生无意义空 `owned`，应移回 MD。**JSON 优先承载可明确判定持有状态的项目**；待内部确认的仍可入表但 `owned` 保持 `""` 并在 MD 注明，不得因难判定而编造「是／否」。

**空缺处理**：v5 结构校验只查类型／长度／唯一性，不查枚举，因此「待核实」与空字符串可以先写入 W；正式应用 P 时，有效行六字段须全非空、`owned∈{是,否}`、`difficulty/barrier∈{低,中,高,待核实}`，否则整维不应用并定位缺项。这正是「合法空缺 → 用户确认更新 W → 人工补全真实内容 → 再验 P」的路径，**不得为通过 P 校验而编造持证状态**。

结构示意（仅示键与取值域，**不含任何业务数据，禁止照抄为成果**）：`{"format":"v5","rows":[]}`；行键集合固定为 `id,name,grade,expiry,owned,difficulty,barrier`。`dim03-seed.json` 的 `groups`＋中文键是旧格式，不得作为输出模板。

## 7. 输出前自检

1. T1—T7 每条有结论或明确的未找到说明；2. 每条证据有等级与七项锚点，事实/判断/建议已分类；3. 无编造持证状态、无示例数据、无虚构引用，法规／强制认证／持证事实均有可靠证据，无检索工具或授权资料时未把空成果标为成功；4. MD 为完整档案且含第 5 节来源对照；5. JSON 严格符合第 6 节并能通过 `valid_dim03_snapshot`；6. MD 与 JSON 同源同版本、JSON 事实均可追溯；7. 未写 W/D/P、未发布 P。任一项不满足须在成果中显式标注未满足项，不得默默交付；不得用 Mock、占位 Skill 或静态 MD 冒充研究成果。
